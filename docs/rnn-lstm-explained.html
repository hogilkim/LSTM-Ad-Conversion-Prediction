    PART 00

    Ground floor

    Ten ideas. Every later part is built out of these. If you already know vectors and gradient descent, skim; if a symbol in Part 4 is unfamiliar, come back to its definition here.

    0.1  A number, a vector, a shape

    A neural network is a machine that does arithmetic. It cannot handle the word cart or a date or a product name. Everything — the input, the memory, the answer — has to be numbers first. So the very first vocabulary is about how numbers get grouped.

    scalar a single number. 3.7, -0.25, 0. When people say “a scalar” they mean “just one number”, as opposed to a whole list of them.
    vector an ordered list of numbers, written [0.2, -1.1, 0.5]. Ordered matters: the first slot always means the same thing as the first slot, so [0.2, -1.1, 0.5] and [-1.1, 0.2, 0.5] are different vectors. This one has three slots, so it is a 3-dimensional vector, written x ∈ ℝ3. Read that as “x is one of the lists of 3 real numbers”. ℝ is just the set of all ordinary numbers; the superscript is how many of them.
    dimension how many slots a vector has. Confusingly, people also say “a 64-dimensional hidden state” to mean a vector with 64 slots. Same thing. Nothing to do with physical space.
    matrix a rectangular grid of numbers — a stack of vectors, all the same length. A matrix with 2 rows and 3 columns has shape (2, 3). Rows first, always.
    tensor the generic word for “a block of numbers with any number of axes”. A scalar is a 0-axis tensor, a vector is 1-axis, a matrix is 2-axis, and a batch of 32 sequences of 50 events each holding 37 numbers is a 3-axis tensor of shape (32, 50, 37). PyTorch calls all of them Tensor. That is the only reason the word exists here.

    You will see shapes constantly, so get in the habit of reading them out loud. (32, 50, 37) is “32 users, 50 events each, 37 numbers describing each event”. Almost every bug in this kind of code is a shape that means something other than what you thought.

    0.2  The weighted sum, which is the whole machine

    The core learned operation in a neural network is repeated a few million times: multiply each input by a number that says how much it matters, add the results up, then add one more number. Non-linearities and gates decide how those weighted sums are used.

    z  =  w1x1 + w2x2 + w3x3 + b
      =  w · x + b
    The second line is the first line, abbreviated. w · x is called the dot product: multiply the two lists slot by slot, then add up all the products. It turns two vectors into one scalar.
    • xthe input. Facts about the thing you are looking at, as numbers.
    • wthe weights. One per input slot. These are what the network learns. A weight near 0 means “this input is irrelevant”. A large positive weight means “when this input goes up, the answer goes up”. Negative means the opposite.
    • bthe bias. One extra number, added no matter what. It is the answer when every input happens to be 0. Without it, the machine is forced to say 0 for an all-zero input, which is rarely what you want.
    • zthe score. Just the result of the arithmetic on the left: every input times its weight, all added up, plus the bias. It can come out as any number — −812.4, 0.003, 57. In particular it is not a probability yet, and that is exactly the problem 0.4 exists to solve.
    two names for z You will meet this same number under two different names. They are not two different things — the name depends only on where the number sits.
    • pre-activation — literally “the value before the activation function”. An activation function is the squashing step you are about to meet in 0.4. So pre-activation just means the number before squashing. Every layer in a network produces one.
    • logit — the same kind of number, but the name is reserved for the network’s last one: the final score, the one that is about to be turned into a probability. So every logit is a pre-activation, but only the final pre-activation is called a logit.

    Concretely: if the network’s final score is z = 2.1, then 2.1 is the logit and σ(2.1) = 0.89 is the probability. Two numbers, two names, one prediction. This matters later for one practical reason — PyTorch’s BCEWithLogitsLoss is named after it, and the name is an instruction: “give me z, not the probability — I will apply the sigmoid myself.” 0.8 explains why doing it that way round matters.

    0.3  Matrix multiply is just several weighted sums at once

    One weighted sum gives you one number. That is a single opinion about the input. Usually you want many opinions at once — “is this user browsing?”, “is this user about to buy?”, “has this user gone quiet?” — computed from the same input with different weights.

    So you stack the weight vectors into a grid. Each row of the matrix is one complete set of weights, producing one output number. That is the entire idea; matrix multiplication is not a new operation, it is a stack of the operation you already know.

    Naming

    When you read Wxxt in Part 2, that is this picture: a matrix of learned weights meeting one event’s numbers, producing one opinion per hidden slot. Nothing more exotic is happening.

    0.4  Squashing: sigmoid and tanh

    A weighted sum can produce any number: -812.4, 0.003, 57. Two problems with leaving it like that.

    1. Stacking weighted sums buys you nothing. If layer two takes a weighted sum of layer one’s weighted sums, the result is W2(W1x) = (W2W1)x — still one weighted sum, just with a different matrix. Ten layers collapse into one. To get anything more expressive than a straight line you must put a non-linear function between the layers. That is the entire job of “activation functions”.
    2. Unbounded numbers can escalate. If the memory of an RNN can grow without limit, repeatedly multiplying it by a matrix can make activations explode. Squashing keeps the hidden state in a bounded range. (Gradients can still explode or vanish; Part 3 separates that issue.)
    σ(z)  =  1 / (1 + e−z)    →   always between 0 and 1
    tanh(z)  =  (ez − e−z) / (ez + e−z)   →   always between −1 and 1
    e is the base of the natural exponential, about 2.71828. These functions are conventionally written with it, and it gives them especially tidy derivatives. Software computes it; you never need to do so by hand.

    The shape is the point, not the formula. Both functions are S-curves. They take the whole infinite number line and fold it into a finite range, gently in the middle and very flatly at the edges.

    sigmoid  σ mathematically outputs a number in (0, 1). It only approaches the endpoints, although floating-point arithmetic can round an extreme result to exactly 0 or 1. σ(0) = 0.5. Because its output is a fraction between none and all, it is the natural choice for a gate: from “let almost nothing through” to “let almost everything through”.
    tanh mathematically outputs a number in (−1, 1), and tanh(0) = 0. Because it can go negative and is centred on zero, it is the natural choice for a value: a piece of information that can point either way. It bounds the LSTM candidate, and tanh(Ct) supplies the value that the output gate turns into ht.

    One sentence to carry forward: sigmoid is used for “how much”, tanh is used for “what”. If you remember only one thing about activation functions in an LSTM, remember that.

    0.5  Element-wise multiply, written ⊙

    This is the operation that makes gating work, and it is the one people most often confuse with the dot product. There are three different “multiplies” and they return three different things.

    OperationWrittenExampleResultReturns
    dot productw · x[2, 3] · [4, 5]2(4) + 3(5) = 23one scalar
    matrix multiplyW x(2,3) × (3,)—a vector, length 2
    element-wisea ⊙ b[2, 3] ⊙ [4, 5][2(4), 3(5)] = [8, 15]a vector, same length

    Element-wise multiply is also called the Hadamard product. In PyTorch it is plain a * b, while matrix multiply is a @ b.

    Now the reason it matters. Suppose the memory is a vector of 64 numbers, and you separately have a vector of 64 fractions between 0 and 1. Multiply them element-wise and you get: keep 3% of slot 1, keep 97% of slot 2, keep 51% of slot 3… — a per-slot volume control. No slot can affect any other slot. That is a gate.

    0.6  Embeddings: turning an ID into a vector

    A row of the Taobao file looks like this:

    1000012,3721104,2465336,cart,1511961600
user_id item_id category_id behavior timestamp

    2465336 is a category ID. It is a name written as a number, not a quantity. Category 2465336 is not “twice” category 1232668, and the two are not “close” because their digits are close. If you feed the raw ID to a network, the network will assume otherwise, because arithmetic is all it does.

    1. First, renumber. The category vocabulary recorded for this run has 6,964 rows: index 0 for padding, index 1 shared by rare or unseen categories, and 6,962 frequent category IDs scattered across a much larger numeric range. For the walkthrough below, suppose a vocabulary maps 2465336 → 917. The choice of 917 is illustrative and carries no meaning; it only gives the ID a compact row number.
    2. The honest but wasteful fix: one-hot. Give each of the 6,964 vocabulary rows its own slot. Index 917 becomes a vector of 6,964 numbers that are all 0 except a single 1 in position 917. Now no ordinary category index is bigger or closer than any other — the one-hot vectors are equally far apart. Correct, but a 6,964-long vector of almost entirely zeros for every one of 50 events is wasteful.
    3. Notice what multiplying a one-hot by a matrix actually does. Treat the one-hot as a row vector and multiply it by a table of shape (6964, 32): uTE. In each of the 32 output sums every term is multiplied by 0 except one, so the answer is simply row 917 of E. You did 32 long sums to recover a row you could have looked up.
    4. So skip the multiply and do the lookup. Store a table with 6,964 rows and 32 columns. To encode category #917, read row 917. That table is an embedding, and in PyTorch it is nn.Embedding(6964, 32).
    5. The table is learned, not designed. The 6,964 × 32 = 222,848 numbers start out random. Training nudges them so that categories which behave alike end up with similar rows. Nobody tells the model that phone cases and phones are related; if that relationship helps predict purchases, the training signal pushes their rows together. This is the single most important thing embeddings buy you: similarity that no one had to hand-write.

    Those five sentences are the whole idea, and step 3 is doing most of the quiet work. “Every term is multiplied by a 0 except one” is easy to write down and easy to nod along to without ever seeing it happen. So here is the same journey again, one stage at a time, with every number on screen.

    Try itFrom one ID to 32 numbers, one stage at a time

    Seven stages, each doing exactly one thing to the number 2465336. Nothing between them is skipped: the renumbering, the one-hot, the multiply written out term by term, the moment that multiply turns out to be unnecessary, and where the result lands in this model. Arrow keys work too.

    Two details from those stages are worth pinning down before moving on, because both come back later. First, an embedding lookup is algebraically the same as a bias-free linear transform of a one-hot vector (allowing for whether vectors are written as rows or columns), with the pointless arithmetic skipped. In the backward pass only rows that appeared in the batch receive non-zero gradients. Second, indices 0 and 1 are special tokens, not ordinary categories. Row 0 is padding and is pinned at zero; row 1 is shared by categories seen fewer than five times. Four observations can move an embedding, but usually provide too little evidence to estimate a useful category-specific vector, so pooling rare categories reduces variance and table size.

    In the implemented model

    Two embedding tables. Categories: nn.Embedding(6964, 32, padding_idx=0). Behaviours: nn.Embedding(5, 4, padding_idx=0) for the four types pv, cart, fav, buy mapped to 1–4, with 0 left for padding. Item IDs get no table in version 1 — 552,000 items × 32 would be 17.7 million parameters, and the median item appears only 17 times in training, which is far too little to learn a meaningful row from.

    0.7  What a derivative is, with no calculus assumed

    Part 3 is the important part of this page, and it is entirely about derivatives. So here is the whole idea, built from “how steep is this hill”.

    1. Slope of a straight line. Go along by some amount (the run), see how far up you went (the rise). Slope is rise / run. A slope of 3 means “every step right, three steps up”. A slope of −0.2 means “every step right, a fifth of a step down”.
    2. Curves do not have one slope, they have a different slope everywhere. On the curve y = x², at x = −2 you are going steeply downhill; at x = 0 you are flat; at x = 2 you are going steeply uphill. So “the slope” only makes sense at a specific point.
    3. Measure it by taking a shorter and shorter run. Pick your point x. Step a small distance h to the right, look at the rise, divide. That gives an approximate slope. Now shrink h. As h gets tiny, the answer stops wobbling and settles on a single number.
    4. That settled number is the derivative. Written dy/dx, or f′(x). Read dy/dx as “how much y changes per unit change in x, right here”. For y = x² it works out to exactly 2x — the demo below lets you watch that happen.
    5. Why any of this matters for a neural network. Replace “x” with “one particular weight” and “y” with “how wrong the model is”. Then the derivative answers exactly the question training needs: if I nudge this weight up a hair, does the error go up or down, and how fast? That number is called the gradient of that weight.
    Try itShrink the run until the slope stops moving

    The curve is y = x². The straight line touches it at two points, h apart. Drag h down towards zero and watch the measured slope converge on 2x — the true derivative at that point.

    0.8  Loss, gradient descent, and what “training” means

    At its core, training is a loop of four things. Architectures and optimisers add details, but they do not change this basic loop.

    1. Predict. Run the input through the network. Out comes a raw score z, then p = σ(z), a number between 0 and 1 that the model is asserting as the probability of a purchase.
    2. Score the prediction with a loss function. The truth y is 0 or 1. The loss is a single number saying how bad p was.
    3. Ask every weight how it contributed. Compute dLoss/dw for each of the tens of thousands of weights. This is backpropagation, and it is nothing but the chain rule (0.9) applied mechanically.
    4. Nudge every weight downhill. w ← w − η · dLoss/dw. The minus sign is what makes it descent: if the gradient is positive (raising this weight raises the loss), you lower the weight. η is the learning rate, the size of the step. Repeat a few hundred thousand times.
    log loss also called binary cross-entropy. The loss used here: L = −[ y log(p) + (1−y) log(1−p) ]. Only one of the two halves is ever alive, because y is 0 or 1. If the truth is 1, the loss is −log(p); if the truth is 0, it is −log(1−p).
    log the natural logarithm. All you need from it here is its shape near zero: log(1) = 0, log(0.5) ≈ −0.69, log(0.01) ≈ −4.6, and it dives towards −∞ as the input approaches 0. With the minus sign in front, that means: being confidently wrong is punished without limit, while being right costs almost nothing.
    Try itWhy confident and wrong is so expensive

    Both curves are the same function, one for each possible truth. Drag the prediction. Note the asymmetry in steepness, not just height: the further you are from the truth, the harder the gradient shoves you back.

    In this project

    The loss is nn.BCEWithLogitsLoss, which takes the raw score z rather than the probability p. It applies the sigmoid and the log together, internally, in a rearranged form that never computes log(0). Doing it yourself as BCELoss(sigmoid(z)) is mathematically identical and numerically worse. A confident enough z rounds σ(z) to exactly 1.0 in floating point, so log(1−p) becomes log(0). PyTorch does not crash — BCELoss clamps its log term at −100, so the loss stays finite — but the gradient that reaches z comes back as 0 instead of the correct ±1. The model receives no learning signal from precisely the examples it is most confidently wrong about, and nothing in the log tells you. BCEWithLogitsLoss rearranges the algebra so the gradient stays exactly σ(z) − y at any magnitude. Always hand it logits.

    0.9  The chain rule — the only rule backpropagation uses

    Weights deep inside a network do not touch the loss directly. They change something, which changes something else, which eventually changes the loss. The chain rule says how to follow that path.

    If   L  depends on  b,  and  b  depends on  a,  then
       dL/da  =  dL/db  ×  db/da
    Multiply the sensitivities along the path. If b moves 4 units for every unit of a, and L moves 3 units for every unit of b, then L moves 12 units for every unit of a.

    A concrete instance you can check by hand. Let a = 2, let b = a², let L = 3b.

    1. Forward. b = 2² = 4, so L = 3 × 4 = 12.
    2. Local sensitivities. db/da = 2a = 4 (from 0.7). dL/db = 3, because L is 3 times b.
    3. Chain them. dL/da = 3 × 4 = 12.
    4. Check it the long way. Substituting, L = 3a², whose derivative is 6a = 12. Same answer. The chain rule did not approximate anything.

    Longer paths just mean more factors in the product:

    dL/da  =  dL/de × de/dd × dd/dc × dc/db × db/da
    Five links, five factors, all multiplied together. Hold onto this sentence — a long path means a long product — because in Part 3 the path is 49 links long and the product is what destroys the RNN.

    0.10  The words used around the model

    These are not part of an LSTM. They are the vocabulary the rest of this page borrows from the project, and every one of them shows up later without warning unless it is pinned down now.

    minibatch 0.8 said “repeat a few hundred thousand times” without saying what one repeat looks at. It is not the whole dataset and not one example: it is a batch of a few hundred, here 256. Gradients are averaged over the batch, then the weights move once. Cheap enough to do constantly, big enough that the average is not pure noise. One complete pass over every training example is an epoch.
    optimizer the rule that turns gradients into weight updates. The plain version is 0.8’s w ← w − η · dL/dw, called SGD. Adam, used here, keeps a running record of each weight’s recent gradients and gives each its own effective step size — weights with consistently small gradients get larger steps. In practice it converges faster and is far less sensitive to the learning rate you pick. opt.step() in the training loop is this rule firing.
    overfitting the model memorising the training examples instead of learning the pattern behind them. You detect it by watching two numbers diverge: training loss keeps falling while validation loss starts rising. Every technique called regularisation exists to fight it — dropout (randomly zeroing part of a layer during training), early stopping (halting when validation stops improving), and simply not giving the model 17.7 million item-embedding parameters to memorise with.
    baseline the simplest model worth beating, reported next to every result so a number means something. Here it is logistic regression on hand-counted features — and you have already built it: a weighted sum (0.2), a sigmoid (0.4), log loss (0.8), trained by gradient descent. That is the entire algorithm. The interesting question is never “is the LSTM good” but “is it better than that, and by how much”.
    ablation deliberately removing one component, retraining, and measuring what the metric loses. It is how you attribute a result to a cause rather than assuming one. Removing the recurrence — replacing the LSTM with an order-free average — is the ablation that says whether order carries signal at all.

    AUC, and why a pure score shift leaves it unchanged

    AUC is the metric this project reports and the one early stopping watches, so it is worth understanding rather than accepting.

    1. Sort every example by the probability the model gave it. Ignore the probabilities themselves; keep only the ordering.
    2. Pick one real buyer and one real non-buyer at random. Ask: did the model rank the buyer above the non-buyer?
    3. AUC is how often the answer is yes. A tied pair counts as half a win. 0.5 means the model orders the classes no better than chance, 1.0 means every buyer outranks every non-buyer, and 0.7 means a random buyer beats a random non-buyer 70% of the time after that tie convention.
    4. Which is why AUC is called rank-based, and why that matters here. Apply the same monotonic transformation to every score and the ordering does not change, so AUC does not move. Log loss does move, because it scores the probability values. A change in base rate can often look like a calibration shift, but a real weekend is also a different population: its ranking difficulty may change too. A uniform recalibration cannot move AUC; an actual distribution shift can.

    PART 01

    Why an ordinary network can’t read a sequence

    Two obvious fixes present themselves. Both fail, and understanding how they fail is what defines the shape of the thing that replaces them.

    Here is the actual task. A Taobao user has done some things — viewed a product page, favourited something, added something to a cart. You are standing at midnight on 1 December 2017 and you want a probability: will this user buy anything in the next 24 hours?

    the input the user’s last 50 events strictly before the cutoff. Each event is a category ID, a behaviour type, and how many hours before the cutoff it happened.
    the label 1 if any buy event falls in the 24 hours after the cutoff, 0 otherwise. In this dataset that is 1 about 14.7% of the time on the training cutoffs.

    A normal feed-forward network wants one fixed-length vector in, one number out. A sequence is neither fixed-length nor a vector. So how do you cram it in?

    Attempt 1 — average the events together

    Turn each event into a vector, add up all 50, divide by 50. Now you have one vector of fixed size no matter how many events there were. Simple, and it genuinely solves the length problem.

    It also destroys the answer. Consider two users with an identical set of six events, in different orders:

     oldest    newestaveragereading
    User Apvpvfavpvpvcart0.3167carted a minute ago — probably buying
    User Bcartpvfavpvpvpv0.3167carted, then drifted — probably abandoned

    Same six events, same average, opposite conclusions. Any order-free summary hands both users the identical input vector and is therefore mathematically incapable of telling them apart.

    Why this matters here

    Cart-then-continue-browsing and browse-then-cart are plausible examples of patterns that counts alone cannot separate. Whether this dataset contains enough such signal to improve AUC is an empirical question, not something the architecture proves. That is why a masked mean-pooling ablation matters: it measures how much performance survives when order is removed.

    Attempt 2 — glue all 50 events into one long vector

    Order preserved this time: stack event 1’s numbers, then event 2’s, and so on, into a single vector of length 50 × 37 = 1850. Feed that to a normal network. Three problems, in increasing order of seriousness.

    1. It is rigid. The network now has exactly 2050 input slots. A user with 7 events does not fit; a user with 80 does not fit. You are back to padding and truncating, which is not itself fatal but shows the design is fighting the data.
    2. It is enormous. A first layer mapping 2050 inputs to 64 hidden units is 131,200 weights. The recurrent model that replaces it will do the same job with about 27,000, because it reuses one small set of weights 50 times instead of owning 50 separate sets.
    3. It does not build in generalisation across positions — and this is the real killer. The weights that directly read event #7 are entirely different numbers from those that directly read event #33. So “a cart is a strong buying signal” has to be represented separately at each position unless the network manages to recover that regularity indirectly through later layers and the training distribution. A cart at position 7 directly updates position-7 weights, not position-33 weights. You have taken one reusable pattern and split its evidence fifty ways.

    What the fix has to look like

    Collecting the three requirements those failures imply:

    1. Handle any length from 3 events to 50, without a different architecture for each.
    2. Respect order — a recent cart must be able to mean something different from an old one.
    3. Share one set of weights across all positions so that every cart anywhere in the sequence contributes evidence to the same “what does a cart mean” parameters.

    There is a design that satisfies all three at once, and it is almost embarrassingly simple: read the events one at a time, and carry a running summary from each step to the next.

    PART 02

    The RNN

    One formula updates a hidden state as it reads each event. That is the whole recurrent cell; a practical model usually adds an input encoder and an output head around it.

    2.1  Input data, hidden state, and parameters

    The RNN reads one event at a time. At step t, it combines two values: the current event xt and the previous hidden state ht−1. The result is a new hidden state ht.

    event input  xt data for event t: its category embedding, behaviour embedding, and scaled age. It comes from the dataset row being processed.
    hidden state  ht a temporary vector computed after reading event t. It has 64 numbers in this project and summarizes the events read so far. Each sequence starts with h0 = 0. It is not loaded from the dataset, is not a learned parameter, and is not saved as part of the trained model.
    model parameters  Wx, Wh, b the learned weights and biases that control how each hidden state is computed. The same parameters are reused at every timestep and for every user. Training updates these values, and saving the model saves them.
    timestep  t a position in the sequence, counting from the oldest event. Not clock time — event #1 and event #2 might be four seconds apart or four days apart. (Age relative to the cutoff is fed in separately as a feature; see 7.3.)

    The hidden state is necessary because xt describes only the current event. When the RNN processes event 10, h9 carries information computed from events 1–9. Without that connection, event 10 could not affect the prediction differently based on what happened earlier.

    h = zeros(64)                       # new temporary state for this sequence
for x_t in user_events:              # x_t comes from the dataset
    h = rnn(x_t, h)                 # current event + previous state

prediction = head(h)                # use the final hidden state
loss = loss_fn(prediction, label)
loss.backward()                     # gradients flow backward through each h
optimizer.step()                    # only model parameters are updated
    What happens during training

    The forward pass computes h1, h2, …, hT, then uses hT to make a prediction and calculate the loss. Backpropagation follows those computations backward through the hidden states to calculate gradients for Wx, Wh, b and the other model parameters. The optimizer updates the parameters. The hidden states are intermediate computed values: gradients flow through them, but the optimizer does not turn them into permanent learned values.

    2.2  The one formula

    ht  =  tanh( Wx xt  +  Wh ht−1  +  b )
    Everything in Part 2 is this line. Read it as: the new hidden state is computed from the current event and the previous hidden state, using learned parameters.
    • htthe new hidden state, 64 numbers, each squashed into (−1, 1) by the tanh.
    • ht−1the hidden state computed after the previous event. For the very first event this is all zeros.
    • xtthe current event from the dataset, represented as numbers: its category embedding, its behaviour embedding, and its scaled age, all glued end to end. 37 numbers in this project.
    • Wxshape (64, 37). A learned parameter. Controls how the current event affects each of the 64 hidden-state slots.
    • Whshape (64, 64). A learned parameter. Controls how the previous hidden state affects the new one. This matrix is where the trouble in Part 3 comes from.
    • b64 biases, one per slot.
    • tanhsquashes each of the 64 results into (−1, 1) so the hidden state cannot run away to huge values as the formula is applied over and over.

    Recurrent means exactly this: the output of the formula is fed back in as one of its own inputs at the next step. The same function, chasing its own tail down the sequence.

    2.3  Unrolling, and why the boxes are all the same box

    2.4  From the final hidden state to a probability

    After the final event, hT is the model’s summary of the user’s sequence. (T is the standard name for the number of steps in the sequence, so hT means “the hidden state after the last event”. Here T is at most 50.) Turning it into an answer takes one more weighted sum — the head.

    z  =  wout · hT  +  bout    ← one number, any size
    p  =  σ(z)                    ← squashed into (0, 1): the probability of a purchase

    Only the final hidden state is used for this prediction. The intermediate hidden states are computed to carry information forward and to support backpropagation, then discarded after the batch. (In other tasks, such as tagging every word in a sentence, you would use all of them. Not here: there is one question and one answer per user.)

    PART 03

    Why RNNs forget

    Derived from the chain rule in 0.9, one factor at a time. If you can reproduce this section on a whiteboard, you can answer the vanishing-gradient question properly rather than reciting the conclusion.

    3.1  What we are trying to compute, and why it is hard

    Training needs one number per weight: dL/dW, how the loss responds to nudging that weight. Take Wh, the matrix that carries the hidden state forward.

    Here is the awkward part. Wh is not used once. It is used at every single one of the 50 steps. Nudge it and you change h1, which changes h2, which changes h3… all the way to h50, which is the only thing the loss actually sees. So its total effect is the sum of its effect through every step, and the effect through the earliest step has to travel the furthest.

    That earliest path is the one we follow, because it is the one that dies.

    3.2  Write out the chain

    Apply 0.9 along the chain h1 → h2 → … → h50 → L:

    dL/dh1  =  dL/dh50 × dh50/dh49 × dh49/dh48 × … × dh2/dh1
    That is 49 factors multiplied together, one per hop back through time. Everything that follows is about the size of a typical factor.
    backpropagation through time (BPTT) the name for exactly this: unroll the network across the sequence, then run ordinary backpropagation along the unrolled chain. There is no new algorithm. The only new thing is that the chain is now as long as the sequence.

    3.3  Work out one single factor

    Take one hop. From 2.2, with zt naming the thing inside the tanh:

    ht = tanh(zt)   where   zt = Wxxt + Whht−1 + b

    Nudge ht−1 and follow the two links:

    1. Through the matrix. zt contains Whht−1, so dzt/dht−1 = Wh. The other two terms do not contain ht−1, so they contribute nothing.
    2. Through the tanh. dht/dzt = tanh′(zt), and there is a tidy identity for it: tanh′(z) = 1 − tanh(z)². You do not have to take that on faith — you already have it. In 0.4 you dragged the input and watched the dashed tanh′ curve; at z = 0 it read 1 while tanh(0) = 0, and where tanh(z) = 0.9 it read 0.19, which is 1 − 0.81. The identity is why the derivative is expressible in terms of the output alone, which is what makes it cheap to compute during backpropagation.
    3. Chain them. dht/dht−1 = tanh′(zt) × Wh.
    The vector version, so nothing is hidden

    With 64 slots, “the derivative” is not one number but a 64×64 grid: how much does each output slot move when each input slot moves. That grid is called a Jacobian, and the factor is diag(tanh′(zt)) · Wh — the same expression, with tanh′ laid down the diagonal of a matrix. (diag(v) means: take the vector v and build a square matrix that is zero everywhere except the top-left-to-bottom-right diagonal, which holds v. Multiplying by it is the same as multiplying element-wise by v.) Where the scalar story asks whether a factor is bigger or smaller than 1, the matrix story asks how the product of Jacobians stretches the relevant directions. Singular values help describe that stretching: repeated contraction makes gradients vanish, while sufficiently repeated expansion permits them to explode. The exact matrices and directions can change at every step, so the rest of this section deliberately uses a scalar illustration rather than claiming a one-number proof for every RNN.

    3.4  Now look at how big that factor is

    Two things are multiplied. Consider each.

    1. tanh′ is at most 1, and is usually well under it. Its maximum is exactly 1, at z = 0. But it falls away fast: once tanh(z) = 0.9 — a perfectly ordinary, not-especially-saturated hidden value — the derivative is 1 − 0.9² = 0.19. Once the state saturates near ±1, the derivative is nearly 0. Go back to the demo in 0.4 and drag the input past ±3 to see it. So this half of the factor is a number in (0, 1] that is below 1 almost always.
    2. Wh is learned, but shared. The network can learn or initialise this matrix to preserve some directions well. The difficulty is that the same linear map is reused at every step, while the input-dependent tanh′(zt) keeps changing and can squash different directions. There is no explicit per-example “carry this slot unchanged now” control.
    3. So each hop has its own factor, call it λt. In a one-slot RNN the factors are numbers; in a real RNN they are Jacobian matrices. Either way, the backward signal is a long product of factors that can repeatedly shrink or stretch it.
    dL/dh1  =  dL/dh50  ×  λ50 × λ49 × … × λ2
    In the one-slot story, λt = tanh′(zt)Wh. If all 49 factors happened to equal one representative value λ, this product would be λ49. The constant-factor case below is an illustration; the real product uses a different factor at each step.

    Back to the weight we actually wanted

    3.1 asked for dL/dWh and the derivation produced dL/dh1. The bridge is one line. Because Wh is used at every step, its total gradient is the sum of its contributions at every step:

    dL/dWh  =  Σt=1..50  (dL/dht) · (∂ht/∂Wh)

    The second factor is local and well behaved — it only involves step t. It is the first factor that carries the long product, and it is tiny for small t. So the sum is dominated by its last few terms: the weight update is computed almost entirely from what happened recently, which is the same conclusion in the form training actually uses it.

    3.6  What this actually means, said carefully

    The precise claim

    It is not that every vanilla RNN must forget, or that it can never learn a long dependency. The claim is a training tendency: when the relevant Jacobian product has norm below 1 over many steps, the learning signal from an early event becomes tiny beside recent-event gradients. In the constant-factor illustration it is five orders of magnitude weaker at λ = 0.8 and fifteen at λ = 0.5. A vanilla tanh RNN therefore has a strong bias toward learning short-range patterns unless its dynamics stay unusually well conditioned.

    The exploding direction is usually easier to detect, though it need not wait for the loss to become nan. clip_grad_norm_ caps an overlarge gradient norm before the optimiser step. There is no equally simple after-the-fact clipping trick for a signal that has already become tiny; careful initialisation and architecture help, and the LSTM’s direct cell-state path is the next such architectural fix.

    3.7  The same problem shows up in the forward pass too

    Forget gradients for a moment. Just watch information travel. Put a strong signal into a single-slot RNN — say a cart at step 1 pushes the hidden state to 1.0 — then feed 20 uneventful steps and see what is left. With Wh = 0.8 and no further input:

    steps since the cart151020

    For this one-slot example with Wh = 0.8, the repeatedly rewritten state fades to 0.8% of its initial value after 20 quiet steps. This demonstrates a common regime, not a theorem that every trained RNN must decay at that rate.

    Both failures have the same root: the only route from the past to the present runs through a matrix multiply and a squashing function, once per step, with no way around.

    The design brief for Part 4

    Give the memory a second route forward — one that is not matrix-multiplied and not squashed at every step. Then let the network decide, per slot and per timestep, how much to send down it. That is the organising idea behind the standard LSTM equations.

    PART 04

    The LSTM

    Long Short-Term Memory. A second memory that is only ever scaled and added to, plus three learned gates that decide what to erase, what to write, and what to show. Six equations, introduced one at a time.

    4.1  Two memories instead of one

    The RNN had one vector, h, doing two jobs at once: remembering things and being the output. Those jobs conflict. To be a good output it must be squashed and reshaped every step; to be a good memory it must be left alone. The LSTM splits them.

    cell state  Ct the long-term memory. 64 numbers. It runs straight along the top of the diagram from one step to the next. Crucially, no matrix ever multiplies it and no tanh ever squashes it on the way past. The only things that happen to it are: multiply by a fraction, and add something. It is never handed to the prediction head directly — only the gated, squashed copy is. (PyTorch does return it to you, as c_n, so you can carry it between chunks of a long sequence.)
    hidden state  ht the working output. 64 numbers. It is a filtered view of the cell state — whatever part of the memory is relevant right now. This is what the prediction head reads, and it is also what the gates at the next step look at.

    Both are vectors of the same length, and both start at zero.

    4.2  What a gate is, mechanically

    Before any equations: a gate is not a metaphor. It is three concrete operations, always in the same order.

    1. Look at the situation. Glue together the previous output ht−1 and the current event xt into one long vector. Written [ht−1, xt]; gluing two vectors end to end is called concatenation.
    2. Take a weighted sum of it using that gate’s own learned matrix and bias — exactly the operation from 0.2 and 0.3, nothing new.
    3. Squash with a sigmoid so every one of the 64 results lands in (0, 1). Now you have 64 fractions, and you element-wise multiply them into something, exactly as in 0.5.

    First, a notation warning

    Three things about Wf · [ht−1, xt] need saying before you meet it, because the padding derivation in Part 6 depends on all three.

    1. The dot here is a matrix–vector product, not the dot product from 0.2. Unfortunate collision, and it is universal in the literature. Wf is a matrix of shape (64, 101) — 64 rows because there are 64 memory slots, 101 columns because [ht−1, xt] is 64 + 37 numbers glued together. The result is a vector of 64, exactly as in 0.3.
    2. One matrix on a concatenation is the same thing as two matrices added. Split those 101 columns into the first 64 and the last 37 and the arithmetic comes apart cleanly:
      Wf · [ht−1, xt]  =  Whf ht−1  +  Wxf xt
      Not an approximation — the two forms are literally the same sum, regrouped. Papers write the left form because it is compact; PyTorch stores the right form, as weight_ih_l0 and weight_hh_l0. Remember the right-hand form. It is why a padding step with xt = 0 still moves the state: the Whfht−1 half is untouched.
    3. The single bf is two biases in the code. Because PyTorch keeps the input and recurrent matrices apart, it stores two full bias vectors as bias_ih_l0 and bias_hh_l0; the forget-gate slices are often written bif and bhf. They are added together in the standard LSTM equations, so writing one bf loses nothing — but it is why the parameter count in 4.10 charges 128 bias parameters per gate rather than 64.
    The trick, in one sentence

    Because a gate is computed from ht−1 and xt, it is different at every timestep and different for every user. A vanilla RNN also reacts to its current input, but its old state always crosses the same recurrent matrix and the same tanh-shaped bottleneck. The LSTM adds an explicit, input-dependent carry control: it can keep a cell slot nearly unchanged for many steps, then erase it when the context changes. That controllable carry path is the central advance.

    4.3  The forget gate — what to erase

    ft  =  σ( Wf · [ht−1, xt]  +  bf )
    64 numbers, each mathematically in (0, 1). Slot by slot: what fraction of the old memory do I keep? Values rounded to 1.0 keep nearly all of it, values rounded to 0.0 wipe nearly all of it, and 0.5 halves it.

    “Forget gate” is a slightly unfortunate name — a value of 1 means remember completely. Read it as a keep gate and it stops being confusing.

    A plausible thing it might learn on this data: hold a slot meaning “this user has an item sitting in their cart, unbought” wide open across dozens of page views, then close it when a buy arrives, because the deliberation is over and the slot should not keep predicting a purchase that already happened.

    Honesty note

    That is an illustration of the kind of thing gates can represent, not a measured fact about any trained unit. Nobody assigns meanings to slots; the network is free to use all 64 in some distributed way that has no clean English description. Do not claim in an interview that a particular unit does a particular thing unless you have gone and looked.

    4.4  The input gate and the candidate — what to write

    Writing takes two separate decisions, and separating them is deliberate.

    gt  =  tanh( Wg · [ht−1, xt]  +  bg )    ← WHAT could be written, in (−1, 1)
    it  =  σ( Wi · [ht−1, xt]  +  bi )      ← HOW MUCH of it to write, in (0, 1)
    Same inputs, different weights, different squashing function — and that difference in squashing is the difference in job. tanh for a value that can point either way; sigmoid for a volume knob. Exactly the rule from 0.4.

    Why two? Because “this event carries important information” and “now is the moment to commit it to memory” are different judgements. Splitting them lets the model propose a strong value and then decline to store it, or store a weak value confidently.

    Naming collision

    The original paper and most textbooks call the candidate C̃t (“C-tilde”). PyTorch’s documentation calls it gt and names it the cell gate, which is doubly confusing since it is not a gate — it is a value. Same object. This page uses gt to match the code you will write.

    4.5  The cell update — the single most important line on this page

    Ct  =  ft ⊙ Ct−1  +  it ⊙ gt
    In English: the new memory is the old memory, partly erased, plus the new proposal, partly written.

    Look at what is absent from that line, compared with the RNN’s ht = tanh(Wxxt + Whht−1 + b):

    1. No matrix multiplies Ct−1. The old memory is scaled by a fraction, element by element. Slot 12 of the old memory becomes slot 12 of the new memory, never mixed into slot 40.
    2. No tanh wraps Ct−1. Nothing is squashed on the way through. The path from Ct−1 to Ct is arithmetically as simple as it gets.
    3. The old and the new are added, not blended through a shared non-linearity. That plus sign is what Part 5 is about. It is the reason the whole architecture works.

    4.6  The output gate — what to show

    ot  =  σ( Wo · [ht−1, xt]  +  bo )
    ht  =  ot ⊙ tanh( Ct )

    Two questions this raises, both worth answering because both get asked.

    1. Why a tanh on Ct here, when 4.5 made such a point of not squashing it? Because this tanh is on the branch, not on the main line. The cell state continues to the next timestep unsquashed; a copy is squashed on its way out. The distinction matters: C is a running sum and can drift to large values, and if h inherited that size it would push every gate’s pre-activation far from zero, saturating all the sigmoids. Bounding the copy keeps the gates responsive without touching the memory.
    2. Why have an output gate at all? Because holding something in memory and acting on it now are different. A slot might be tracking “this user browses electronics at night” — worth keeping for fifty steps, irrelevant to the current prediction. The output gate lets the cell keep it and not show it.

    4.7  All six equations, and the wiring

    ft = σ(Wf·[ht−1, xt] + bf)    forget — how much old memory to keep
    it = σ(Wi·[ht−1, xt] + bi)    input — how much new value to write
    gt = tanh(Wg·[ht−1, xt] + bg)  candidate — the value on offer
    ot = σ(Wo·[ht−1, xt] + bo)    output — how much memory to expose
    Ct = ft ⊙ Ct−1 + it ⊙ gt          the memory update
    ht = ot ⊙ tanh(Ct)                    the working output
    The first four lines are the same weighted-sum-then-squash, four times over with different weights. Only the last two lines are new machinery, and both are element-wise. That is the whole architecture.

    PART 05

    Why the gradient survives

    Part 3 showed the gradient dying in a product of 49 factors. Here is what those factors become in an LSTM — plus the caveat that most explanations leave out.

    5.1  Differentiate the cell update

    Same procedure as 3.3, on the line from 4.5. One new symbol first.

    ∂ a curly d. It means exactly what d meant in 0.7 — a derivative, a rate of change — and is used when the thing you are differentiating depends on several inputs and you want the rate with respect to just one of them, holding the others still. Ct depends on Ct−1, ft, it and gt, so ∂Ct/∂Ct−1 is “how Ct moves when only Ct−1 moves”. Nothing else changes. It is called a partial derivative, and everything in 0.9 applies to it unchanged.
    Ct = ft ⊙ Ct−1 + it ⊙ gt
    ⇒   direct-path derivative, with gate outputs held fixed  =  ft
    Along the explicit cell-state edge, Ct−1 appears once and is multiplied by ft; the add does not shrink that nudge. This gives a clean path with no recurrent matrix and no tanh′. The full derivative also includes indirect paths through ht−1 and the gates; 5.3 draws the distinction carefully.

    A derivative is “how much does the output move when I nudge the input” (0.7) — so here is that nudge, pushed through one cell update and, for comparison, through one RNN step.

    one direct contribution to ∂L/∂C1  =  ∂L/∂C50  ×  f50 × f49 × … × f2
    The full gradient is a sum of computational paths. This particular path is still a product of 49 numbers, but the network chooses them one per slot per step. If keeping a slot alive lowers the loss, training can drive those forget-gate values towards 1 so this contribution survives.

    Put the sentence in the form you would say out loud in an interview:

    The answer

    An LSTM does not guarantee that gradients never vanish. It adds a direct route through the cell state whose per-step factor is a learned, input-dependent forget-gate value rather than a recurrent matrix followed by tanh. The model can set that factor close to 1 for the slots and timesteps where memory matters. The additive cell update is what creates this easier gradient route.

    5.3  The caveat that most explanations skip

    1. The full derivative is not just ft. The gates are computed from ht−1, which itself depends on Ct−1. So the computational graph contains the direct cell-state edge with factor ft plus indirect routes through the output, gates, and candidate. Those extra terms can reinforce or cancel the direct one, and they also participate in products across time. The defensible claim is narrower and stronger: the gradient contains a direct additive path that avoids a recurrent matrix and tanh at every hop. The product of forget gates describes that path’s contribution, not the entire derivative.
    2. A forget gate below 1 still decays, just slowly. With f = 0.99 at every step, 49 steps still leaves 0.61 — fine. With f = 0.9, you are back to 0.0057, which is exactly the RNN’s problem. The LSTM makes long memory possible and learnable; it does not make it automatic.
    3. At length 50 the advantage may be modest. The vanishing-gradient story is most dramatic at lengths of hundreds or thousands. Fifty steps is short, so a well-tuned vanilla RNN is not hopeless here. The logistic-regression baseline already exposes strong recency features; only the eventual validation and test results can say whether gating buys a meaningful AUC lift.

    5.4  The GRU, in full

    The Gated Recurrent Unit is a related gated RNN that is easiest to compare with an LSTM using two simplifications: no separate cell state, and old-versus-new mixed by a single update gate. If you keep a fraction z of the old value, the new candidate gets 1−z — so one number does both jobs.

    rt = σ(Wr·[ht−1, xt] + br)    reset — how much old state the candidate may see
    zt = σ(Wz·[ht−1, xt] + bz)    update — forget and input in one number
    nt = tanh(Winxt + bin + rt ⊙ (Whnht−1 + bhn))  candidate
    ht = (1 − zt) ⊙ nt + zt ⊙ ht−1            the update
    The last line is still “old times a fraction, plus new times a fraction, added” — so the gradient argument in 5.1 carries over unchanged, with zt playing the part of ft. Three gate-sized matrices instead of four, so about 25% fewer parameters. Two placement details in the third line are PyTorch’s convention and differ from some papers, so copy them exactly: rt is applied after the recurrent matrix multiply rather than to ht−1 before it, and the recurrent bias bhn sits inside that product while bin sits outside.

    Neither GRU nor LSTM dominates across datasets; parameter count, speed, and validation performance decide. In PyTorch the constructor swap is one word: nn.LSTM(…) becomes nn.GRU(…). The return value also changes: a GRU returns only h_n, not an (h_n, c_n) pair.

    PART 06

    Batches, padding, and the trap

    The gap between the mathematics above and code that actually trains. This is where the quiet bugs live — the kind that do not crash and do not error, they just make the model worse and never tell you.

    6.1  Why sequences get padded

    1. Processors want rectangles. Running one user at a time wastes almost all of a CPU or GPU. You want to process 256 users at once, which means one tensor holding all of them: shape (256, T, 37) — 256 users, T timesteps, 37 numbers per event. From here on B is the standard name for that first number, the batch size, so the same shape is written (B, T, 37) or, since T is fixed at 50 here, (B, 50, 37).
    2. But users have different lengths. In this dataset, between 3 and 50 events, averaging around 31 to 41 depending on the cutoff. A tensor cannot have ragged rows.
    3. So you pad. Fill every short row out to length 50 with a filler value — index 0, which is reserved and never a real category or behaviour. Real events first, filler after: right padding.
    4. And you record the real length. A separate lengths tensor of shape (256,) says where each row’s real data stops. Everything in the rest of this section depends on having that.
    Try itWhich timestep does the model actually read?

    A batch of four users padded to a common length. Switch the readout mode and watch which cell gets picked up as “the summary of this user”. The first mode reads the wrong cell for every row that is not full length; the other two read the right one, by different routes.

    6.2  Why zero padding is not automatically harmless

    The intuition “the padded events are all zeros, so they contribute nothing” sounds right and is wrong. Walk through what the cell actually does on a padding step.

    1. The input vector really is zero. With padding_idx=0, the embedding row for index 0 is all zeros and receives no gradient. So xt = 0 for a pad step. So far so good.
    2. But the gates do not only depend on xt. The forget gate is ft = σ(Wf·[ht−1, 0] + bf) = σ(Whfht−1 + bf). The ht−1 half survives, and so does the bias. There is no reason on earth for that to equal exactly 1.
    3. So the state keeps moving. Ct = ft ⊙ Ct−1 + it ⊙ gt with f, i, g all non-zero. The memory decays and gets written to during the padding, and then ht = ot ⊙ tanh(Ct) changes too.
    4. A zero input is a real input. The layer has no idea the row ended. It runs 50 steps because you handed it 50 steps. For a user with 8 real events, 42 of the steps that produce the final state are hallucinated from nothing.

    Why this is a real bug

    Taking h_n straight from an unpacked padded batch gives the state at t = 49, not the state at each row’s last real event. The implemented model avoids this by packing, and test_conversion_lstm_ignores_positions_after_each_length changes every value after a row’s declared length and asserts that its logit is exactly unchanged. The validation-size effect against an intentionally wrong unpacked version is still unknown until training results are recorded.

    6.3  Three correct fixes

    The first two produce the identical vector for a unidirectional model read at its last state, by two different routes — and knowing why they are equivalent is a better interview answer than knowing either one alone. The third is not an alternative to them: it is what you do when you are not reading a last state at all.

    Fix 1 — packing

    from torch.nn.utils.rnn import pack_padded_sequence

packed = pack_padded_sequence(x, lengths.detach().cpu(), batch_first=True, enforce_sorted=False)
out_packed, (h_n, c_n) = self.lstm(packed)
# h_n is now the state at each row's own final real step. Shape (1, B, 64).
summary = h_n[-1]                              # (B, 64)

    What packing physically is, since “it handles it for you” is not an answer. Take four sequences of lengths 5, 3, 2, 1. Packing throws away the padding and stores the real steps time-major, along with a count of how many rows are still alive at each timestep:

    enforce_sorted=False lets you pass the batch in any order; PyTorch sorts internally and unsorts the result. Without it you would have to sort every batch by length yourself. lengths must live on the CPU even when the data is on a GPU — a small, well-known annoyance.

    Fix 2 — index the unpacked output at each row’s last real step

    out, _ = self.lstm(x)                          # (B, 50, 64), padding included
idx = (lengths - 1).to(out.device)               # (B,) last REAL position per row
rows = torch.arange(out.size(0), device=out.device)
summary = out[rows, idx]                              # (B, 64)

    Read the indexing carefully, because it is the part people find opaque. torch.arange(B) is [0, 1, 2, …], one entry per row. idx is [4, 2, 1, 0, …], one entry per row. Pairing them elementwise picks out[0,4], out[1,2], out[2,1], out[3,0] — a different timestep for every row, all in one operation. This is called advanced indexing.

    The padding steps are still computed and then discarded, so this wastes a little arithmetic. In exchange it skips the pack/unpack overhead entirely, and at a fixed T = 50 on CPU it is usually the faster of the two. Both are correct.

    Fix 3 — mask, when you pool instead of taking a last state

    # WRONG: divides by 50 and averages in the padding
pooled = x.mean(dim=1)

# RIGHT: zero the pad positions, then divide by the real length
lengths_x = lengths.to(x.device)
positions = torch.arange(x.size(1), device=x.device)
mask = (positions[None, :] < lengths_x[:, None]).unsqueeze(-1)
pooled = (x * mask).sum(dim=1) / lengths_x.unsqueeze(-1)

    That mask code is the densest on this page, so take it apart. First lengths is copied to the same device as x; this matters on a GPU even though packing itself requires CPU lengths. torch.arange(50) is [0, 1, 2, …, 49]. [None, :] turns it into a (1, 50) row. lengths_x[:, None] is a (B, 1) column. Comparing them gives a (B, 50) true/false grid by broadcasting: an axis of size 1 is repeated to match. Each row asks “is position t less than this user’s length?” unsqueeze(-1) adds a trailing axis so the mask can multiply the (B, 50, 37) tensor across all 37 features.

    Two traps stacked in the ablation

    The mean-pooling baseline is the experiment most likely to be silently wrong, and it has two independent failure modes. First, dividing by 50 instead of seq_len systematically shrinks the pooled vector for short sequences — the model then partly learns to read length off the magnitude. Second, the hours feature is padded with 0. The cutoff rule makes an exact 0 impossible — events are strictly before the cutoff — but an event two minutes before it scales to 0.0004, which is the same number to the model. Unmasked, every padding step reads as a fresh event at the cutoff moment, and a user with 3 real events gets 47 imaginary ones dated to right now. Get this wrong and mean pooling looks worse than it is, which flatters the LSTM — the exact direction of error that is hardest to notice.

    6.4  When padding genuinely does not matter

    attention, and the Transformer the main alternative to recurrence, referenced twice below and once in Part 8. Instead of passing a state forward step by step, self-attention lets every position look directly at every other position and take a weighted average of their value vectors, with the weights computed from how well the positions match. A Transformer stacks attention with feed-forward and normalisation layers. Information between two positions has a direct route rather than a recurrence whose path grows with their separation — but self-attention alone has no notion of order, which is why positional information has to be added. The attention weights are produced by a softmax, a function that turns a list of scores into positive fractions summing to 1; masking a position with −inf before that softmax gives it weight 0, which is how padding is excluded.
    setupis right-padding safe?why
    unidirectional, read at last real stepyesthe padding is entirely after the step you read; it cannot influence it
    unidirectional, read at t = T−1nothat is the trap in 6.2 — you read a state built from padding

    Among these raw, unmasked padded computations, the first row is safe. Packing or an explicit mask can make the other architectures length-aware too.

    6.5  Two more traps worth knowing by name

    Trap

    nn.LSTM(…, dropout=0.2) does nothing on a single-layer LSTM. That argument applies dropout between stacked layers, so with num_layers=1 there is no between. PyTorch warns, and the warning is easy to miss in a busy log. If you want dropout, put an explicit nn.Dropout before the linear head.

    Trap

    Feeding raw hours_before_cutoff (0 to 168) alongside embeddings initialised near N(0,1) — a bell curve centred on 0 with most values inside ±1 — lets one feature dominate the first layer by two orders of magnitude before any learning happens. Feed log1p(hours) / log1p(168), which lands in [0, 1] and compresses the difference between 100 and 168 hours — which nobody cares about — while preserving the difference between 1 and 5 hours, which is where the signal is.

    7.2  Cutting one training example out of a user

    An example is not a user. It is a (user, cutoff) pair. Take the cutoff at midnight starting 1 December, UTC+8 — Unix timestamp 1512057600.

    1. The input window. Every event with timestamp < 1512057600, keeping the most recent 50. This user has 12, so all 12 are kept and seq_len = 12. Fewer than 3 and the example is dropped entirely — there is nothing to read.
    2. The label window. Look at [1512057600, 1512144000) — the 24 hours of 1 December. If any buy event falls in there, the label is 1. Otherwise 0. Nothing else about that window is ever shown to the model.
    3. The strict inequality is the whole discipline. Not one number that goes into the input may come from at or after the cutoff. An event at exactly 1512057600 belongs to the label window, not the input. This is what “no leakage” means concretely, and it is a line of code, not a philosophy.
    4. The same user reappears at every cutoff. Six cutoffs: 28, 29, 30 November and 1 December are training (split=0), 2 December is validation (split=1), 3 December is test (split=2). So one user yields up to six examples, each with a different input window and its own label.

    from torch.nn.utils.rnn import pack_padded_sequence

class ConversionLSTM(nn.Module):
    def __init__(
        self, num_categories, num_behaviors,
        category_embedding_dim=32, behavior_embedding_dim=4, hidden_dim=64,
    ):
        super().__init__()
        self.category_embedding = nn.Embedding(
            num_categories, category_embedding_dim, padding_idx=0
        )
        self.behavior_embedding = nn.Embedding(
            num_behaviors, behavior_embedding_dim, padding_idx=0
        )
        self.lstm = nn.LSTM(
            category_embedding_dim + behavior_embedding_dim + 1,
            hidden_dim, batch_first=True,
        )
        self.classifier = nn.Linear(hidden_dim, 1)

    def forward(self, cats, behs, hours, lengths):
        features = torch.cat(
            (
                self.category_embedding(cats),
                self.behavior_embedding(behs),
                hours.unsqueeze(-1),
            ),
            dim=-1,
        )                                                   # (B, 50, 37)
        packed = pack_padded_sequence(
            features, lengths.detach().cpu(),
            batch_first=True, enforce_sorted=False,
        )
        _, (hidden, _) = self.lstm(packed)      # hidden: (1, B, 64)
        return self.classifier(hidden[-1]).squeeze(-1)  # (B,) logits

    Reading that as the story of one user:

    1. Two lookups and a concatenation. Each of the 12 real events becomes 32 numbers describing its category, 4 describing its behaviour type, and 1 for how long ago it happened — 37 numbers per event. Concatenated rather than added, because the three are unrelated kinds of information and there is no reason to force them into a shared space.
    2. Packing removes padding from the recurrence. lengths.detach().cpu() tells PyTorch where every row ends. enforce_sorted=False lets the DataLoader hand over any batch order; PyTorch sorts and restores it internally.
    3. Twelve LSTM steps for this user, not fifty. The packed kernel reads the 12 real events and never executes the 38 padded positions. The returned hidden[-1] is therefore the state immediately after this user’s final real cart, shape (B, 64).
    4. One linear classifier. Linear(64, 1) collapses the user summary into one raw score. There is currently no dropout layer in ConversionLSTM.
    5. Sigmoid, at the end. p = σ(z) is the answer: the probability this user buys something on 1 December. During training the sigmoid lives inside BCEWithLogitsLoss (see 0.8); at inference you apply it yourself.

    7.6  What the memory has to do to be useful here

    Be precise about this, because the loose version of the argument falls apart under questioning. The baseline is not order-blind: hours since last event, hours since last cart-or-fav, events in last 24h and cart count in last 24h all encode timing, which may capture much of what order carries here. That is exactly why it is a strong baseline and why any claimed lift must be measured rather than assumed.

    The sharp version of the claim is this. The baseline compresses the sequence into about ten numbers. Any two sequences that agree on all ten are the same input to it — and the LSTM, which reads the ordered triples themselves, can still tell them apart. Such pairs exist. Here is one, with hours before the cutoff in brackets:

     oldest  newestthe story
    User Apv X [30h]cart X [28h]pv Y [26h]pv Y [2h]researched X, carted it, then moved on to a different category
    User Bpv Y [30h]cart X [28h]pv X [26h]pv Y [2h]carted X, then came back to keep looking at X

    Identical on every count feature: 3 pv, 1 cart, 0 fav, 0 buy, 2 distinct categories, seq_len 4, 2h since the last event, 28h since the last cart-or-fav, 1 event in the last 24h, 0 carts and 0 buys in the last 24h. The difference is only which category was carted relative to which was viewed after — and B, still circling the carted item, is the better prospect.

    So the mechanism the LSTM has and the baseline does not is the ability to bind a behaviour to what it was about and carry that binding forward — the “keep a slot open for this category until something closes it” behaviour you watched the forget gate perform in 4.8.

    The honest frame, and what the planned ablation could control for

    The pair above is a hypothesis about where lift could come from, not a claim about what the trained model does. The not-yet-implemented mean-pooling ablation could turn it into evidence — but be careful about how much it would prove, because this is where the argument is easiest to overclaim.

    Mean pooling would share the embeddings, so those would be controlled for. It would not share capacity. Pooling (B, 50, 37) gives a 37-number vector, and a Linear(37, 1) head on it is 38 parameters; the implemented LSTM-plus-classifier path is 26,433. So that planned ablation would remove order and nearly all the non-embedding capacity at the same time, and a gap between them would be an upper bound on what order contributes, not a measurement of it. To actually isolate order you would pool and then put a comparable-capacity MLP on the pooled vector, so only the ordering is gone.

    And if the LSTM ties mean pooling and mean pooling ties logistic regression, the honest conclusion is that this feature set and this dataset have a ceiling — not that the architecture needs more tuning.

        lengths_array <= upper
    )
    bucket_labels = labels_array[in_bucket]
    if (
        bucket_labels.size == 0 or np.unique(bucket_labels).size != 2
    ):
        auc_by_sequence_length[name] = None
    else:
        auc_by_sequence_length[name] = float(
            roc_auc_score(bucket_labels, probabilities_array[in_bucket])
        )

return EvaluationMetrics(
    auc=float(roc_auc_score(labels_array, probabilities_array)),
    log_loss=float(log_loss(
        labels_array, probabilities_array, labels=[0.0, 1.0]
    )),
    auc_by_sequence_length=auc_by_sequence_length,
)

    PART 08

    Questions you will be asked

    Written the way you would say them out loud — a claim, the mechanism behind it, and the caveat that shows you know where it stops being true.

    Explain how an LSTM mitigates the vanishing-gradient problem.

    In a vanilla RNN the gradient reaching an early step contains a product of Jacobians, one per hop: each combines the shared recurrent matrix Wh with a state-dependent tanh′(zt). Repeatedly shrinking directions vanish and repeatedly expanding directions explode. In the constant scalar example, a factor of 0.8 over 49 hops leaves 1.8×10−5.

    The LSTM adds Ct = ft ⊙ Ct−1 + it ⊙ gt. This creates a direct cell-state path with no recurrent matrix and no tanh between adjacent cell states. That path’s per-step factor is ft, recomputed for every example, slot, and step, so training can push it towards 1 where memory matters.

    The caveat: this does not “solve” vanishing gradients in the sense of making them impossible. The full derivative also has indirect paths because the gates depend on the previous hidden state, and a direct path with f = 0.9 still decays badly. The architecture makes long memory easier to learn; it does not make it automatic.

    Why sigmoid for the gates and tanh for the candidate?

    Sigmoid answers how much — its output is a fraction in (0, 1), which is the meaningful range for a volume control. tanh answers what — its output is in (−1, 1) and centred on zero, which is what a value needs if it is allowed to push a memory slot either up or down.

    What is pack_padded_sequence and why do you need it?

    Sequences in a batch have different lengths but a tensor is a rectangle, so short rows are padded to the maximum. The LSTM does not know a row ended — it runs one step per column it is handed, and a padding step still updates the state, because ft = σ(Whfht−1 + bf) is not 1 just because xt is zero.

    Packing flattens the batch to the real steps only, stored time-major with a batch_sizes array saying how many rows are still alive at each timestep. Rows drop out as they end and are never stepped again, so h_n is each row’s state at its own final real event — correct by construction.

    It is not the only correct option. out[arange(B), lengths-1] on the unpacked output picks the same vector, and at a fixed length of 50 on CPU it is usually faster because it skips the pack/unpack overhead in exchange for computing padding steps it throws away. For a unidirectional last-state readout the two are exactly equivalent.

    Is padding harmless? When is it not?

    Raw right padding is harmless to a unidirectional readout taken at each row’s last real step, because all padding comes later and cannot influence that state. Packing is also safe because padded steps are never run.

    It is not harmless if you read h_n from an unpacked right-padded batch: that is the state after the final padded column. The walkthrough shows why the state moves; a trained-model effect must be measured rather than invented.

    Unmasked padding is also unsafe for a bidirectional layer, because the reverse pass starts inside right padding; packing fixes that and does not create leakage for this sequence-level forecast, since every real event is still before the prediction cutoff. Pooling and attention need masks because they touch every position. Left padding precedes real events and therefore affects an ordinary unidirectional state unless it is handled explicitly.

    Why an LSTM and not a Transformer?

    Not for cost. Attention costs O(L²) — “grows like the square of the sequence length”, since every position attends to every other — but L = 50 means 2,500 pairs, which is nothing.

    The real argument is that a Transformer’s advantage is content-based long-range dependency without a recurrent bottleneck, while these sequences stop at 50 events and the engineered features suggest strong recency effects. There is not yet evidence that a dependency long enough to favour attention is the missing ingredient. Meanwhile self-attention alone has no built-in notion of order: without positional information it treats the inputs as a set, so position has to be injected instead of arising from the recurrence. That injection can be fixed (sinusoidal encodings, no parameters) or learned. Depending on the chosen widths and layers, a Transformer may also add capacity and regularisation sensitivity. The 742,611 snapshots come from about 200K users, so the effective amount of independent evidence is lower than the row count suggests.

    And there is an empirical hook rather than only an argument: slice AUC by sequence length (3–10, 11–30, 31–50). If the LSTM’s edge over mean pooling grows with length, recurrence is doing order-dependent work and a longer-range model may be worth trying. If it does not, test whether order, capacity, or optimisation is the limiting factor before reaching for a larger architecture.

    An LSTM has 4× the parameters of an RNN at the same hidden size. How do you know the gain is from gating and not capacity?

    Fair challenge, and there are two ways to answer it. The clean one is to match parameter counts — compare against an RNN with a larger hidden size that lands near 26,400 recurrent parameters instead of 6,592.

    The cheaper planned ablation is masked mean pooling: it shares the embeddings but has no recurrence. I would be careful not to oversell it, though, and saying so is the better answer. Pooling drops to 37 dimensions with a 38-parameter head against the LSTM’s 26,433, so it removes order and capacity together — the gap is an upper bound on what order contributes rather than a clean measurement. Isolating order properly means pooling and then adding a comparable-capacity MLP head. Either way it answers a question worth more than the original: not “is gating better than no gating” but “does order carry signal in this dataset at all”.

    Your positives are 14.7%. Why no pos_weight or resampling?

    14.7% is imbalanced but supplies over a hundred thousand positive examples. More importantly, the task wants probabilities, and unweighted binary cross-entropy targets the observed class probability. A positive weight of (1−η)/η = 5.79 changes that target. In an intercept-only base-rate calculation, the unweighted optimum has log loss about 0.42, while forcing the weighted optimum near 0.5 gives unweighted log loss about 0.69. Those are sanity-check calculations, not results from a trained LSTM.

    Reweighting can also change AUC because the model is retrained and may learn a different ordering. Exact AUC invariance applies only when a fixed set of scores is passed through a monotonic transformation. If weighting helps ranking, calibrate afterward and report both metrics; do not assume either outcome.

    Since the results table reports overall AUC, log loss and AUC by sequence-length bucket, and since a conversion probability is the kind of number a bid would be computed from, calibration is worth more here than a metric-neutral reweighting.

    What does a time-based split control for, and what does it not?

    It controls for temporal leakage: every input precedes its cutoff, the vocabularies and all weights are fit before the validation cutoff, and no example can see its own future. That is the thing a random split gets catastrophically wrong on sequence data, because a random split lets the model learn from a user’s December behaviour and then predict their November behaviour.

    It does not control for user overlap — 97.9% of test examples are users seen in training, so this measures how well the model rescores a warm population, not cold-start. It does not control for the weekday-to-weekend shift, since the training cutoffs are Tuesday to Friday and validation and test are Saturday and Sunday, which moves the positive rate from 14.7% to about 17.6%. And it does not control for a window artefact: the data starts on 25 November, so the mean age of a user’s oldest retained event grows from 48.8 hours at the first cutoff to 114.0 hours at the last, which means the model could in principle read the cutoff date off the hours feature.

    Those caveats do not automatically invalidate a same-split baseline comparison, but they limit what it proves. Different model families can exploit the window artefact or repeated-user identity differently, so “both models see it” is not a complete control. State the target population and add grouped-user or window-matched sensitivity checks if the claim needs to extend beyond warm daily rescoring.

    What happens if the forget gate gets stuck at 1? At 0?

    Stuck at 1, the direct cell path never erases: Ct = Ct−1 + it ⊙ gt. Its direct gradient contribution is preserved, but other paths can still saturate or interfere. If non-zero writes keep accumulating, the cell can grow, tanh(Ct) can saturate, and the model cannot represent “that intent is over” in that slot.

    Stuck at 0, the cell is wiped every step: Ct = it ⊙ gt, which depends only on the current event and the previous hidden state. You have thrown away the long-term memory and are left with something close to a vanilla RNN.

    Related and worth knowing: some implementations initialise bf to 1 so the gate starts open and the model remembers by default, on the argument that it is easier to learn to forget than to learn to remember. PyTorch does not do this — it initialises all LSTM parameters uniformly in ±1/√hidden — so it is a manual change if you want it.

    Why did you drop item embeddings?

    552,305 item-vocabulary rows at 32 dimensions would add about 17.7 million parameters, roughly 70× the rest of the model. Among encoded item rows used by training examples, the median frequency is 17 and 84.5% appear fewer than 50 times, so many embeddings would be estimated from little evidence and carry a high memorisation risk.

    Category is a more tractable first level: 6,964 vocabulary rows over the same events. Running the item-embedding version as an ablation is still worth doing — it tests whether any lift is robust or largely item-level memorisation, which is also relevant to the repeated-users concern.

    Glossary

    Every term used on this page, defined again without needing the surrounding text.

    activation functionA non-linear function applied after a weighted sum. Without one, stacked layers collapse into a single layer.
    AUCArea under the ROC curve. The probability that a randomly chosen positive is ranked above a randomly chosen negative, with ties counting half. 0.5 is chance, 1.0 is perfect. Depends on ranking, not calibration.
    backpropagationComputing the derivative of the loss with respect to every weight, by applying the chain rule backwards through the network.
    BPTTBackpropagation through time. The same algorithm applied to an unrolled RNN, so the chain is as long as the sequence.
    batchA group of examples processed together in one forward and backward pass, stacked into one tensor.
    batch_firstA PyTorch flag choosing whether tensors are shaped (batch, time, features) or (time, batch, features). The default is the second; almost everyone sets it to the first.
    biasA constant added after a weighted sum. The output when every input is zero.
    calibrationWhether predicted probabilities match observed frequencies — of everything the model calls 30% likely, do about 30% happen? Log loss is sensitive to it; AUC is not.
    candidate  gtThe new value an LSTM proposes writing into memory, in (−1, 1). Written C̃t in papers, gt in PyTorch.
    cell state  CtAn LSTM’s long-term memory. Only ever scaled by a gate and added to — never matrix-multiplied or squashed on its way between timesteps.
    chain ruleIf L depends on b and b depends on a, then dL/da = dL/db × db/da. Multiply the sensitivities along the path.
    concatenationGluing two vectors end to end into one longer vector. Written [a, b].
    cutoffThe moment that divides an example’s input from its label. Everything strictly before is input; the 24 hours after define the label.
    derivativeThe slope of a function at a point — how much the output moves per unit of input. Written dy/dx.
    dropoutRandomly zeroing a fraction of a layer’s outputs during training only, so the next layer cannot depend too heavily on any one of them.
    element-wise multiply  ⊙Multiply two equal-length vectors slot by slot, giving a vector. Also called the Hadamard product; a * b in PyTorch. Distinct from the dot product, which gives a scalar.
    embeddingA learned lookup table mapping an ID to a vector. Mathematically identical to multiplying a one-hot vector by a matrix, done as a lookup instead.
    epochOne complete pass over the training set.
    exploding gradientThe per-step factor exceeding 1, so the product grows without bound and weights jump wildly. Fixed by gradient clipping.
    forget gate  ftThe sigmoid gate that decides what fraction of each memory slot to keep. Better read as a “keep” gate: 1 means remember completely.
    gateA vector of values in (0, 1), computed from the current input and previous hidden state, multiplied element-wise into something to control how much passes.
    gradientThe derivative of the loss with respect to a parameter. Its sign says which way to move the parameter; its magnitude says how much the loss cares.
    gradient clippingRescaling a gradient whose norm exceeds a threshold. A standard safeguard for exploding gradients; it does not restore a signal that has already vanished.
    GRUGated Recurrent Unit. A gated RNN with no separate cell state; one update gate blends old state and new candidate. Three gate-sized parameter groups instead of an LSTM’s four.
    hidden state  htThe network’s working memory and output at step t. In an LSTM it is a gated, squashed view of the cell state.
    h_nPyTorch’s final hidden-state tensor, shape (D×num_layers, B, hidden), where D is 2 for bidirectional and 1 otherwise. For an unpacked, right-padded, unidirectional batch it is the state after the final padded column, not each row’s last real event. Packing makes it length-aware.
    JacobianThe grid of derivatives of every output with respect to every input. The vector-valued generalisation of a derivative.
    learning rate  ηHow far to move each weight along its gradient at each step. Too large and training diverges; too small and it crawls.
    logitThe raw score before a sigmoid. Any real number. Loss functions ending in WithLogits want this, not the probability.
    log1p(h)Shorthand for log(1 + h). Used because it is defined at h = 0, where a plain log is not, and because it compresses large values far more than small ones.
    log lossBinary cross-entropy, −[y log p + (1−y) log(1−p)]. Punishes confident wrong answers without limit.
    LSTMLong Short-Term Memory. An RNN with a separately maintained cell state and three gates governing what is erased, written and exposed.
    maskingExplicitly excluding padded positions from a computation. Mandatory whenever an operation touches every position, such as pooling or attention.
    one-hotA vector that is all zeros except a single 1, marking which category something is.
    output gate  otThe sigmoid gate controlling how much of the (squashed) cell state becomes the hidden state.
    packingStoring a padded batch as only its real steps, time-major, with a count of live rows per timestep, so the layer stops each row at its own length.
    paddingFilling short sequences with a reserved value so a batch forms a rectangle. Index 0 here, by convention.
    padding_idxAn nn.Embedding argument pinning one row to zero and excluding it from gradient updates.
    parameterA number the network learns — a weight, a bias or an embedding row. With the recorded 6,964-category vocabulary and current defaults, this model has 249,301 of them.
    poolingCollapsing a sequence of vectors into one by averaging or taking a maximum. Order-free, so it bounds what recurrence contributes — though it removes capacity along with order, so the bound is an upper one.
    recurrentFeeding a function’s output back in as one of its own inputs at the next step, so one set of weights handles a sequence of any length.
    RNNRecurrent neural network. In its plain form, ht = tanh(Wxxt + Whht−1 + b).
    scalar / vector / matrix / tensorOne number; an ordered list; a rectangular grid; a block with any number of axes.
    seq_lenHow many real (unpadded) events a sequence contains. 3 to 50 in this project.
    shapeThe size of a tensor along each axis, as a tuple. (256, 50, 37) is 256 users, 50 timesteps, 37 features.
    sigmoid  σ1/(1+e−z). Squashes any number into (0, 1). Used for gates and for turning a logit into a probability.
    tanhSquashes any number into (−1, 1), centred at 0. Used for values rather than fractions. Its derivative is 1 − tanh(z)².
    timestepA position in a sequence, counted from the oldest event. Not clock time.
    unrollingDrawing a recurrent loop as a chain of copies, one per timestep. A drawing convention — all the copies share one set of weights.
    vanishing gradientRelevant directions in the per-step Jacobians repeatedly contract, so their product becomes tiny and learning from early timesteps becomes difficult.
    ablationRemoving one component, retraining, and measuring what the metric loses — how you attribute a result to a cause instead of assuming one.
    AdamThe optimizer used here. It tracks moving averages of each parameter’s gradient and squared gradient, producing parameter-wise adaptive updates. It is often a convenient default, but still needs a sensible learning rate and does not universally outperform SGD.
    attentionAn alternative to recurrence: every position looks directly at every other and takes a weighted average, weights computed from how well the positions match. No state to squeeze through, but also no built-in notion of order.
    baselineThe simplest model worth beating, reported next to every result so a number means something. Here, logistic regression on hand-counted features.
    bidirectionalRunning two recurrent passes over the available sequence, one forward and one backward, then combining them. Unpacked right padding corrupts the reverse pass, so use packing or an equivalent mask. It is safe for this sequence-level forecast because every real event is before the prediction cutoff; it would leak only in an online per-timestep task that forbids looking at later events in the same sequence.
    broadcastingWhen two tensors disagree on an axis and one has size 1 there, that one is silently repeated to match. What makes arange(50)[None,:] < lengths[:,None] produce a full (B, 50) grid.
    cold startPredicting for a user or item the model has never seen. This project does not measure it — 97.9% of test examples are users seen in training.
    early stoppingHalting training when validation performance stops improving, and keeping the best checkpoint rather than the last. A form of regularisation.
    logistic regressionA weighted sum, a sigmoid, and log loss, trained by gradient descent. Everything in 0.2, 0.4 and 0.8 combined. The baseline this project has to beat.
    minibatchThe few hundred examples one weight update is computed from — not one example, not the whole dataset. 256 here.
    optimizerThe rule that turns gradients into weight updates. opt.step() is it firing.
    overfittingMemorising training examples instead of learning the pattern behind them. Detected by training loss falling while validation loss rises.
    partial derivative  ∂A derivative with respect to one input of several, holding the others still. Everything about the chain rule applies to it unchanged.
    rank-basedDepending only on the ordering of a fixed set of predictions, not their values. AUC is; log loss is not. A monotonic recalibration leaves AUC unchanged, but a real population shift can change the ordering difficulty too.
    regularisationAnything done to fight overfitting: dropout, early stopping, fewer parameters, stopping the model memorising individual items.
    softmaxTurns a list of scores into positive fractions summing to 1. Feeding it −inf at a position forces that position’s weight to exactly 0 — how attention masks padding.
    TransformerA stack of attention layers. The main alternative to an LSTM here, and argued against in Part 8 on grounds of what the data contains rather than cost.
    weightA learned multiplier on an input, saying how much that input contributes.
    weight sharingUsing one set of parameters at every position, so evidence from all positions trains the same numbers. What makes an RNN sample-efficient compared with a flattened network.
